# نظام الحلقات

نظام إدارة حلقات تحفيظ القرآن — **جمعية أفضلكم لتعليم القرآن الكريم وعلومه**.

يغطي دورة العمل اليومية كاملة: التحضير، الحفظ الجديد، المراجعة، المستويات والاختبارات
والشهادات، تذاكر الترفيه الأسبوعية، الاعتماد المالي، وإشعار أولياء الأمور.

---

## التقنيات

| الطبقة | التقنية |
|---|---|
| الواجهة والخادم | Next.js 16 (App Router, Server Components, Server Actions) |
| التنسيق | Tailwind CSS 4 |
| قاعدة البيانات والمصادقة | Supabase (Postgres + Auth + Row Level Security) |
| الاستضافة | Vercel |

اللغة JavaScript لا TypeScript. الواجهة عربية بالكامل واتجاهها RTL على مستوى المستند.

---

## التشغيل محلياً

```bash
cd web
npm install
npm run dev
```

يتطلب ملف `web/.env.local` (غير مرفوع — انظر قسم البيئة):

```
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_ANON_KEY=...
```

## قرارات تصميمية تشرح الكود

هذي أهم ما يحتاج المبرمج معرفته قبل أي تعديل.

### ١. المحرك القرآني مصدر واحد لا يُعدَّل

`lib/quranEngine.js` منسوخ حرفياً من `engine/quranEngine.js` — محرك مُختبَر مسبقاً
ومعتمَد من الجمعية. **لا يُعدَّل.** يبني التغطية كمجموعة (Set) من أرقام الآيات
المطلقة، ويشترط تغطية **كل** آيات الربع قبل اعتماده (0 أو 1، لا نسب مئوية).

`lib/quran-boundaries.js` يحوي حدود 240 ربعاً و604 صفحات لمصحف حفص، محوَّلة إلى
`{surah, ayah}`. تطابق بياناتها 100% ما يعيده `api.alquran.cloud/v1/meta` — وهو
المصدر الذي كان التطبيق السابق يجلبه وقت التشغيل. تضمينها داخل الكود يزيل الاعتماد
على الإنترنت أثناء التشغيل.

### ٢. اتجاه الحفظ من الناس صعوداً

الحفظ يبدأ من الناس (114) نحو البقرة (2)، لا العكس. تنعكس هذي القاعدة في ترتيب قوائم
السور، وفي `targetSurahOrder()`، وفي ترتيب وحدات المراجعة.

### ٣. الجديد والمراجعة نظامان منفصلان

- **الجديد** يتبع هدفاً يعيّنه المشرف، ويُحتسب وحده في التقدم وجاهزية الاختبار
  والإحصائيات. تسجيلات `مراجعة` **لا** تُحتسب — وإلا لدفعت جلسةُ مراجعة طالباً إلى
  "جاهز للاختبار" بلا حفظ جديد.
- **المراجعة** نطاقها محسوب لا معيَّن: اتحاد تغطية الجديد ومدى المستويات المجتازة،
  ويتوسّع تلقائياً كلما تقدّم الطالب.

### ٤. السرد التراكمي وبوابة التسليم

السرد يبدأ كل يوم من **آية 1 من السورة الحالية** إلى نقطة جديدة، لا من حيث توقّف.
ومن المستوى الثاني فما فوق لا تُفتح السورة التالية قبل تسليم السابقة واعتمادها
(`surah_deliveries`). البوابة مطبَّقة داخل الـ Server Action لا في الواجهة فقط.

### ٥. موضع دورة المراجعة محسوب لا مخزَّن

`stepCounter` = عدد تسجيلات المراجعة للطالب، فلا يوجد مؤشر مخزَّن يمكن أن يفقد
تزامنه مع السجل. يصحّ هذا لأن الوحدات مرتَّبة من الناس تنازلياً، والحفظ يتقدّم نحو
أرقام سور أقل، فالوحدات الجديدة تُضاف دائماً في آخر القائمة ولا تزحزح المواضع السابقة.

### ٦. الوثائق الرسمية تُجمَّد وقت الإصدار

الشهادة تحفظ **التقدير** لا الدرجة وحدها، والتذكرة وخطاب الاعتماد يحفظان قيمهما وقت
الإصدار. تعديل سلّم التقديرات لاحقاً لا يغيّر أي شهادة صادرة.

### ٧. ما يمكن حسابه لا يُخزَّن

نسبة التقدم، السورة الحالية، نصيب المراجعة، حالة الطالب — كلها تُحسب لحظياً من
`daily_records`. المخزَّن فقط ما هو واقعة مستقلة: تسجيل يومي، محاولة اختبار، تسليم
سورة، تذكرة صادرة.

### ٨. الحماية على ثلاث طبقات

RLS في Postgres يمنع رؤية بيانات فرع آخر. وحماية الأدوار في `lib/auth.js` تمنع الوصول
إلى صفحة أو تنفيذ إجراء خارج الدور. **كل Server Action يتحقق بنفسه** — فهو نقطة وصول
مستقلة عن الصفحة التي تعرضه.

والطبقة الثالثة في القاعدة نفسها: مُشغِّلات على `daily_records` ترفض السجل المخالف حتى
لو جاء من خارج التطبيق (لوحة Supabase مثلاً). فقاعدة السرد التراكمي وقفل ما بعد
الاختبار ليست عرفاً في الكود، بل شرطاً لا يمر بدونه إدخال.

## قاعدة البيانات

كل ما تحتاجه القاعدة موجود في `database/` — الجداول والدوال والسياسات والمُشغِّلات.
الملفات مقروءة من القاعدة الحيّة لا مكتوبة من الذاكرة، فهي تطابق المطبَّق.

### بناء قاعدة جديدة من الصفر

تُشغَّل هذي الملفات بهذا الترتيب في محرّر SQL:

| # | الملف | الغرض |
|---|---|---|
| ١ | `schema.sql` | الجداول والمفاتيح والقيود |
| ٢ | `rls-policies.sql` | الدوال المساعدة وسياسات عزل الفروع |
| ٣ | `rls-restrictive.sql` | تضييق صلاحيات التعديل والحذف |
| ٤ | `surah-ayah-counts.sql` | جدول مرجعي بعدد آيات كل سورة |
| ٥ | `triggers.sql` | حرّاس `daily_records` |
| ٦ | `trigger-ayah-bounds.sql` | النسخة النافذة من دالة التحقق |

الترتيب ليس اختيارياً: السياسات تستدعي الدوال، والمُشغِّل الأخير يقرأ جدول عدد الآيات.

### ملفات ترقية قاعدة قائمة

`constraints.sql` و`constraints-2.sql` لا تُشغَّل على قاعدة جديدة — قيودهما مدمجة في
`schema.sql` أصلاً. وجودهما لترقية قاعدة أُنشئت قبل إضافة تلك القيود.

### لماذا لا `supabase db dump`؟

يحتاج Supabase CLI على جهاز، وهذي الملفات بُنيت من استعلامات داخل المحرّر نفسه —
`information_schema.columns` و`pg_constraint` و`pg_policies` و`pg_get_functiondef`.
النتيجة واحدة، والطريق متاح من أي متصفح.

### الجداول

| الجدول | الغرض |
|---|---|
| `branches` | الفروع (عزل بنين/بنات) |
| `users` | المستخدمون وأدوارهم، `id` من نوع `uuid` يطابق `auth.users.id` |
| `halaqat` | الحلقات ومعلموها |
| `students` | الطلاب، ومنهم `parent_phone` لمراسلة ولي الأمر |
| `attendance` | الحضور اليومي، صف واحد لكل طالب في اليوم |
| `daily_records` | السجلات اليومية (`type` = `جديد` أو `مراجعة`) |
| `surah_ayah_counts` | مرجع ثابت: عدد آيات كل سورة (114 صفاً) |
| `student_levels` | مستويات الطالب مرقَّمة بالتسلسل |
| `milestone_log` | المحطات (25/50/75/100%) مربوطة بمستواها |
| `surah_deliveries` | محاولات تسليم السور |
| `exam_results` | محاولات اختبار نهاية المستوى |
| `weekly_tickets` | تذاكر الترفيه الصادرة |
| `financial_requests` | طلبات الاعتماد المالي |

دوال مساعدة `security definer` تتفادى الاستدعاء الدائري في سياسات RLS:
`is_admin()`، `my_role()`، `my_branch_id()`.

## البيئة

متغيرات `web/.env.local` غير مرفوعة إلى المستودع (محمية بـ `.gitignore`)، ومضبوطة
كذلك في إعدادات مشروع Vercel. الـ anon key مصمَّم للكشف في المتصفح وتحميه RLS، لكنه
لا يُرفع إلى المستودع على أي حال.

جذر المشروع في Vercel مضبوط على مجلد `web/`.

## ما جرى التحقق منه فعلياً

لا يكفي أن تكون الحماية مكتوبة — هذي نتائج تشغيل حقيقي على القاعدة والموقع
المنشور، لا استنتاج من قراءة الكود.

### عزل الحلقات والفروع

الاختبار: الدخول بحساب معلم، ثم كتابة `‎/teacher/sard?studentId=N` يدوياً في شريط
العنوان — لأن الرابط مدخل مستقل لا يمر على القائمة التي تعرض طلابه.

| الطالب | علاقته بالمعلم | النتيجة |
|---|---|---|
| 1 | من حلقته | فُتحت الصفحة — وهذا الضابط الذي يثبت أن الطريقة نفسها تعمل |
| 4 | فرعه نفسه، حلقة أخرى | رُدَّ إلى `‎/teacher` بلا عرض |
| 3 | فرع آخر | رُدَّ إلى `‎/teacher` بلا عرض |

الضابط (الطالب 1) ضروري: بدونه لا يمكن التمييز بين رفضٍ حقيقي وبين رابط لم
يُفتح أصلاً — الحالتان تنتهيان بالمنظر نفسه.

والنتيجة أن العزل قائم على **الحلقة** لا الفرع: الطالب 4 في فرع المعلم نفسه ومع
ذلك رُدّ، فمعلم لا يرى طلاب معلم آخر ولو شاركه الفرع.

### تبديل الأدوار

طبقة مستقلة عن السابقة: تلك تحكم أي صفوف تُقرأ، وهذي تحكم أي صفحات تُفتح أصلاً.
الاختبار: تسجيل الدخول بدور، ثم كتابة رابط صفحة خارج الدور يدوياً. الرفض يظهر
كردٍّ إلى `‎/dashboard?denied=1` مع شريط «هذي الصفحة خارج صلاحيات حسابك».

| الدور | الصفحة | النتيجة |
|---|---|---|
| مشرف | `‎/levels` | فُتحت — الضابط |
| مشرف | `‎/executive` | رُدَّ |
| معلم | `‎/review` | فُتحت — الضابط |
| معلم | `‎/levels` | رُدَّ |
| معلم | `‎/finance` | رُدَّ |
| معلم | `‎/executive` | رُدَّ |

الحالة الأخيرة تقصد القفز درجتين لا درجة واحدة. وشريط التنقّل نفسه لا يعرض أصلاً
إلا ما يسمح به الدور، لأن كليهما يقرأ `PAGE_ROLES`.

### مُشغِّلات `daily_records`

| المحاولة | من ردّها |
|---|---|
| `type = 'test'` | `validate_daily_record()` |
| `type = 'جديد'` لطالب بلا مستوى | `block_new_memorization_after_exam()` |
| الناس: آية 200 (وهي ست آيات) | `validate_daily_record()` بعد ربطه بجدول عدد الآيات |

### تضييق الصلاحيات

`pg_policies` تُظهر السبع سياسات `RESTRICTIVE` المكتوبة في `rls-restrictive.sql`،
وجدول `surah_ayah_counts` يحوي 114 صفاً بمجموع 6236 آية.

## ما لم يُنجَز بعد

### الأهم: لا توجد شاشات إدارة، ولا تصحيح للأخطاء

التطبيق **لا يكتب** في `students` ولا `halaqat` ولا `users` ولا `branches` إطلاقاً —
صفر عملية إدراج أو تعديل. فإضافة طالب، أو نقله بين حلقتين، أو إنشاء حساب معلم، كلها
تجري يدوياً من لوحة Supabase. يعمل اليوم ببيانات تجريبية قليلة، لكنه عبء حقيقي مع
بداية كل فصل.

وكذلك **لا يوجد تراجع عن أي إدخال**. لا التطبيق يحذف سجلاً يومياً، ولا سياسات RLS
تسمح لمعلم أو مشرف بذلك (وهذا مقصود — انظر `rls-restrictive.sql`). فمعلم سجّل آية
خطأ، أو مشرف رصد درجة خطأ، أو عيّن مدى مستوى خطأ: التصحيح يتطلب دخول المدير على
لوحة Supabase مباشرة. والأخطاء واقعة لا محالة في الاستخدام اليومي.

هذان أهم ما ينقص قبل التشغيل مع طلاب حقيقيين، وأولى ما يُبنى بعد التسليم.

### أصغر من ذلك

- **`financial_requests.status`**: يُدرَج بقيمة «قيد المراجعة» ولا يُحدَّث أبداً. لا
  توجد شاشة اعتماد أو رفض للطلب المالي — العمود موجود والمسار غير مبني.
- **منهج الجمعية الرسمي**: مدى كل مستوى يُدخَل يدوياً. عند توفّر المنهج يمكن استبدال
  الإدخال الحر بقائمة محدَّدة دون المساس بمنطق المراجعة، لأنه يعتمد على `level_number`
  لا على المدى نفسه.
- **رسائل واتساب**: تعمل عبر روابط `wa.me` — نصف آلية، تتطلب ضغطة إرسال. الأتمتة
  الكاملة تتطلب حساب WhatsApp Business API.
- **صلاحية المشرف عبر الفروع**: العزل تام حالياً، ولا يوجد مشرف يرى الفرعين.
- **الشعار**: 324×176 بكسل، كافٍ للشاشة وضعيف للطباعة عالية الجودة.
- **بيانات المهرة القديمة**: لم تُهاجَر — التطبيق السابق خزّن مجاميع تراكمية لا مديات
  دقيقة، فلا يمكن استيراد سجلاتها إلى محرك التغطية الحالي بدقة.
